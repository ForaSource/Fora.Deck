# Сборка XLibrary для Windows и Linux

Актуальная полная SemVer-версия задаётся файлом [`VERSION`](VERSION), например
`0.4.0`, `0.4.0-rc.1` или `0.4.0-rc.1+build.7`. Её строка сохраняется
в приложении, manifest и именах Windows/AppImage-пакетов. Примеры имён
пакетов нужно заменять при изменении `VERSION`.
Реализованный GUI использует **Qt Widgets**; QML и Qt Quick для сборки не нужны.

## Общая упаковка выпуска из Windows

После настройки Windows Release запустите Docker Desktop с Linux containers
и PowerShell 7 из корня репозитория. Linux-пакеты собираются в Debian 13:

```powershell
pwsh -File ./packaging/package_project.ps1
# Посмотреть план без сборки и создания файлов:
pwsh -File ./packaging/package_project.ps1 -WhatIf
# Только Windows или Linux:
pwsh -File ./packaging/package_project.ps1 -Platform Windows
pwsh -File ./packaging/package_project.ps1 -Platform Linux
# Альтернатива: заранее настроенный Debian 13 в WSL:
pwsh -File ./packaging/package_project.ps1 -Platform Linux -LinuxEnvironment WSL -WslDistribution Debian
```

Скрипт вызывает существующие упаковщики: Windows получает portable ZIP и
Inno Setup EXE, Linux — AppImage и DEB. Для Windows используется настроенный
`cmake-build-release`, другой каталог задаётся через `-WindowsBuildPath`.
По умолчанию `-LinuxEnvironment Docker`: target `linux-packaging` в корневом
`Dockerfile` создаёт образ `xlibrary-linux-packaging:debian13` с системными
Qt 6.8.2 и glibc 2.41. Проверка Docker и подготовка образа выполняются до
Windows-сборки. Первая подготовка загружает Debian и пакеты через APT.
Исходники подключаются к контейнеру только для чтения, сборка выполняется
в новом `/build` внутри контейнера; кэш сборки Ubuntu не используется.
Результаты записываются в каталог выпуска, а инструменты и исходники Qt
сохраняются в Docker volume `xlibrary-linux-packaging-cache-debian13`.
После успеха контейнер удаляется, образ и volume остаются для повторной упаковки.
При сбое контейнер сохраняется вместе с `/build` и `/tmp`; сообщение содержит
его имя для `docker logs` и `docker cp`. После диагностики удалите этот
контейнер командой `docker container rm <имя>`.

Для `-LinuxEnvironment WSL` нужен отдельный Debian 13 с настроенным Release
и системным Qt 6.8.2. Только в этом режиме используются `-WslDistribution`
и `-LinuxBuildPath` (по умолчанию `cmake-build-linux-release`). Linux-путь
может быть абсолютным путём WSL; относительный отсчитывается от корня
репозитория. Без `-WslDistribution` проверяется дистрибутив WSL по умолчанию.
Неподходящий дистрибутив или настроенный Qt отклоняется до Windows-сборки.
Также нужны `pkg-config` и `libsecret-1-dev`, как в командах ниже.

Результат — `release/v<версия из VERSION>/windows-mingw/` (или `windows-msvc/`),
`linux-x86_64/` и **один** `SHA256SUMS.txt` в корне выпуска. Манифест содержит
SHA256 всех файлов в подпапках, включая `build-info.json`, кроме самого
манифеста; пути относительные, с `/`, формат совместим с `sha256sum --check`.
Суммы отдельных платформ заменяются общим файлом. Проверять его нужно из
корня папки выпуска, например в WSL:

```sh
cd /mnt/f/XLibrary/release/v0.3.2
sha256sum --check SHA256SUMS.txt
```

Inno Setup 6.3+ ищется в `PATH` и стандартных папках установки Inno Setup 6/7; другой путь
передайте через `-InnoCompiler`. Параметры `-MsvcRuntimePath`,
`-CompilerLicensePath`, `-QtSourceManifest` передаются Windows-упаковщику.
`-QtSourceCache` задаёт кэш исходников Qt (по умолчанию
`build/windows-packaging-cache`). При повторной упаковке архивы из кэша
проверяются по SHA256 и используются без скачивания. Для загрузки нужен `curl.exe`
(входит в современные Windows и GitHub runner). Каждая из трёх попыток ограничена
300 секундами на всю передачу и 20 секундами на соединение; скорость ниже
1 КиБ/с в течение 30 секунд прерывает попытку. В лог выводятся размер, время
и средняя скорость передачи. Неполный файл не попадает в кэш. Для работы без
загрузки исходников можно заранее положить в кэш соответствующие
`qtbase-everywhere-src-<Qt-версия>.tar.xz`, `qtsvg-...` и архивы других
фактически используемых модулей из `packaging/qt_sources.json`.
После загрузки упаковщик отдельно сообщает о проверке SHA256, копировании
архива и извлечении лицензий. Лицензии извлекаются через настроенный CMake
(`cmake -E tar`), без выбора `tar` из `PATH`, с лимитом 120 секунд на архив.
Диагностика извлечения сохраняется в `build_path/packaging-release.log`;
при ошибке staging остаётся для разбора.
`-ReleaseNotes путь.md` добавляет предоставленный файл как `RELEASE_NOTES.md`
и включает его в манифест. Требования платформенных упаковщиков сохраняются,
включая сетевой доступ для загрузки зависимостей и исходников Qt.

Существующая папка `v<версия>` не перезаписывается. Для повторной сборки
используйте другой `-OutputRoot`, например `-OutputRoot release/rebuild`.
При ошибке скрипт останавливается без общего манифеста; частичные результаты
сохраняются для диагностики. `-WhatIf` показывает версию и каталог результата,
но не проверяет готовность toolchain. Скрипт не меняет `VERSION` при запуске.

## Linux и CLion

Нужны Linux с `/proc`, компилятор C++23 (GCC 13+ или Clang 17+ с соответствующей libstdc++), CMake 3.21+, Ninja и Qt **6.5+** с Widgets, Concurrent, Network и DBus. Для глобального сочетания и переключения окон в X11 установите заголовки Xlib. Без Xlib сборка поддерживается, но эти две функции недоступны. Qt для Windows нельзя использовать при сборке Linux.

Например, в Debian **13** системный Qt **6.8.2** удовлетворяет минимальной версии:

```sh
sudo apt-get update
sudo apt-get install build-essential clang cmake ninja-build qt6-base-dev qt6-wayland qt6-tools-dev qt6-l10n-tools libx11-dev libsecret-1-dev pkg-config
cmake --preset linux-debug
cmake --build --preset linux-debug --parallel 4
./cmake-build-linux-debug/XLibrary
```

В других дистрибутивах установите аналогичные development-пакеты. Если системный Qt старее 6.5, установите Linux Qt отдельно и передайте `-DCMAKE_PREFIX_PATH=/path/to/Qt/gcc_64`. SQLite и QtKeychain 0.17.0 загружаются с проверкой хеша. QtKeychain связывается статически; на Linux для сборки нужны pkg-config и libsecret-1-dev. Для автономной конфигурации можно указать уже проверенные исходники: `-DFETCHCONTENT_SOURCE_DIR_SQLITE3=/absolute/path/to/sqlite-amalgamation` и `-DFETCHCONTENT_SOURCE_DIR_QTKEYCHAIN=/absolute/path/to/qtkeychain-0.17.0`.

Личный GitHub-токен хранится через QtKeychain: Windows Credential Manager или системное хранилище Linux (Secret Service/KWallet). На Linux нужен запущенный и доступный сервис, например GNOME Keyring или KWallet. Сохранение открытым текстом запрещено. Без настроенного токена сервис секретов не требуется. Токен привязан к локальному пути профиля и пользователю ОС; после переноса portable-профиля его нужно ввести заново.

В `CMakePresets.json` есть профили `linux-debug`, `linux-release`, `linux-clang-debug`, `windows-debug`, `windows-release` с раздельными каталогами. На Linux:

```sh
cmake --preset linux-release
cmake --build --preset linux-release --parallel 4
cmake --preset linux-clang-debug
cmake --build --preset linux-clang-debug --parallel 4
cmake --install cmake-build-linux-release --prefix "$HOME/.local"
```

Предупреждения `/W4` (MSVC) или `-Wall -Wextra -Wpedantic` включены для
собственных GUI и core. Для ограниченного анализа ошибок из `.clang-tidy`
нужны CMake **3.27+**, Ninja/Makefiles и `clang-tidy` соответствующего toolchain:

```bash
cmake --preset linux-clang-debug -DXLIBRARY_ENABLE_CLANG_TIDY=ON
cmake --build --preset linux-clang-debug --parallel 4
```

Анализ выполняется при компиляции собственных `.cpp`; SQLite, Qt/keychain,
сгенерированные moc/RCC и системные заголовки исключены. CI включает его
для Linux Clang Debug и Windows MSVC Debug (Ninja с окружением MSVC).
Остальные обычные сборки не требуют `clang-tidy`.

Установка Linux добавляет `bin/XLibrary`, ярлык в `share/applications`, значок и лицензию. Для неё нужны системные runtime-пакеты выбранного Qt и Xlib. Если использован отдельный Qt SDK, настройте поиск его библиотек для установленного приложения. Добавьте `$HOME/.local/bin` в PATH для запуска из меню. Для разработки установка приложения не требуется.

В CLion откройте корневой `CMakeLists.txt`, загрузите CMake presets и включите нужный профиль в **Settings → Build, Execution, Deployment → CMake**. Для Linux выберите Linux toolchain. На Windows с WSL выберите toolchain **WSL / Ubuntu**, Linux CMake и Linux Qt внутри WSL. Если профиль скрыт условием ОС Windows-хоста, создайте WSL CMake profile вручную: Build directory `cmake-build-wsl-debug`, Build type `Debug`, без Windows `CMAKE_PREFIX_PATH`. Для Windows выберите совместимые Qt и MSVC/MinGW, как описано ниже. Выберите цель `XLibrary` и Build/Run/Debug. Пользовательские пути храните в игнорируемом `CMakeUserPresets.json`. Не переносите Windows PATH и `QT_QPA_PLATFORM_PLUGIN_PATH` в Linux-конфигурацию запуска.

Особенности Linux:

- Обнаружение использует XDG `.desktop`; пользовательские записи имеют приоритет. Учитываются `Hidden`, `NoDisplay`, `OnlyShowIn`, `NotShowIn`, `TryExec`, локализованные названия, `Exec`, `Icon`, `Path`, `Terminal` и D-Bus activation. Аргументы пользователя добавляются к `Exec`, shell-подстановок нет. При заданных аргументах или рабочем каталоге D-Bus не используется для запуска. Команда «Запросить новый экземпляр» всегда использует `Exec` и недоступна для записей без рабочей команды `Exec`; само приложение может повторно использовать существующее окно. Для `Terminal=true` нужен установленный терминал.
- Можно добавлять абсолютные пути к исполняемым файлам, AppImage и скриптам с shebang и разрешением `+x`. Расширение не обязательно; регистр путей учитывается. AppImage требует его собственных runtime-зависимостей. Статус читается из `/proc`; wrapper, заменяющий себя другим executable, может не сопоставиться с записью. Flatpak/Snap учитываются по доступным метаданным процесса; `hidepid` и права ограничивают наблюдение.
- БД: `$XDG_DATA_HOME/XLibrary/xlibrary.db`, иначе `~/.local/share/XLibrary/xlibrary.db`. Настройки: Qt AppLocalDataLocation, обычно `~/.local/share/XLibrary/XLibrary/settings.ini`. Portable-флаг рядом с бинарником включает каталог `data`; `--check-startup` использует временный профиль. Автозапуск: `$XDG_CONFIG_HOME/autostart`, иначе `~/.config/autostart`.
- Встроенное глобальное сочетание и запрос переключения чужого окна доступны в X11. В Wayland назначьте сочетание в настройках рабочего стола для команды `XLibrary`: второй запуск передаёт запрос работающему экземпляру. Переключение чужих окон ограничено композитором; при недоступности выполняется обычный запуск. Трей зависит от рабочего стола; без трея закрытие завершает приложение, а фоновый старт показывает окно.
- Эффекты рамки Windows доступны только Windows. Linux использует Qt и системное оформление окон. Нативные UI-плагины Linux — `.so` в `plugins` рядом с бинарником, собранные с совместимыми Qt и C++ ABI.

Проверка запуска с временным профилем:

```sh
./cmake-build-linux-debug/XLibrary --check-startup
QT_QPA_PLATFORM=xcb xvfb-run -a dbus-run-session -- ./cmake-build-linux-debug/XLibrary --check-startup
QT_QPA_PLATFORM=offscreen ./cmake-build-linux-debug/XLibrary --check-startup
```

Для Xvfb нужны `xvfb`, `xauth`, `dbus-x11` и runtime-зависимости Qt xcb. CI собирает GCC Debug/Release и Clang Debug, проверяет X11-старт и системную установку. Интерактивные сценарии рабочего стола и пользовательские приложения требуют проверки в конкретной среде.

## Linux: AppImage portable и установщик DEB

Из корня проекта, после конфигурации `linux-release`:

```sh
python3 packaging/build_release.py
# Только один формат или другой каталог результата:
python3 packaging/build_release.py --format appimage --output-path release/appimage
python3 packaging/build_release.py --format deb --output-path release/deb
```

Нужны Python **3.11+**, `curl`, `file`, `dpkg-dev`, `desktop-file-utils` и динамический Qt. Скрипт проверяет Release, архитектуру x86_64 и `XLIBRARY_NATIVE_CPU=OFF`, сам собирает программу и проверяет запуск пакетов. В `release/v<версия>-linux/` создаются AppImage, `.deb`, `SHA256SUMS.txt` и `build-info.json`. Существующий каталог результата не перезаписывается; для повторной упаковки выберите новый `--output-path`. Временная упаковка выполняется в Linux `/tmp`, чтобы сохранялись Unix-права и ссылки, в том числе при WSL и исходниках на NTFS.

**AppImage** включает Qt, платформенные плагины X11/Wayland, C++ runtime, лицензии и исходники Qt. Инструменты упаковки загружаются по фиксированным версиям из `packaging/appimage_tools.json` и проверяются по SHA256. Для системного Qt нужны включённые `deb-src` репозитории: упаковщик получает точную версию исходного пакета и исправления дистрибутива через `apt-get source --download-only`. Для официального Qt SDK используются проверенные исходные архивы из `packaging/qt_sources.json`; неизвестные версии и библиотеки останавливают упаковку.

Кэш Linux-упаковщика хранится в `$XDG_CACHE_HOME/XLibrary/packaging`, а если
переменная не задана — в `~/.cache/XLibrary/packaging`. В WSL оставляйте его
на файловой системе Linux: кэш на `/mnt/c` или `/mnt/f` может запрещать
`chmod` инструментов AppImage. Другой каталог задаётся через `--cache-path`.

```sh
chmod +x XLibrary-0.2.0-linux-x86_64.AppImage
./XLibrary-0.2.0-linux-x86_64.AppImage
# Если FUSE недоступен, например в некоторых средах WSL:
./XLibrary-0.2.0-linux-x86_64.AppImage --appimage-extract-and-run
```

Версия в имени берётся из `VERSION`. Каталог и настройки сохраняются в `<имя файла>.AppImage.data` рядом с образом. Переносите AppImage вместе с этой папкой и сохраняйте имя файла. Каталог должен быть доступен для записи. Автозапуск указывает на исходный AppImage, а не на временный каталог монтирования. `--check-startup` использует временный профиль и не меняет portable-данные. Программы, запускаемые из библиотеки, получают исходное окружение без подмешивания Qt из AppImage.

**DEB** собирается для Debian 13 и использует системный Qt; пакеты и минимальные версии библиотек определяются `dpkg-shlibdeps`. Упаковка DEB требует Qt, установленный пакетным менеджером: отдельный SDK и Qt новее **6.8.2** для этого формата отклоняются. Системный Qt из testing/unstable тоже может оказаться слишком новым. Платформенные плагины Qt, Wayland и `xdg-utils` объявлены зависимостями. Пакет устанавливает программу в `/usr/bin/XLibrary`, ярлык в меню и значок; пользовательские данные остаются в XDG-профиле.

Debian-версия имеет числовую основу и `~` перед prerelease: любой RC меньше
финальной версии. Идентификаторы prerelease кодируются по типу и ASCII-порядку,
чтобы сохранить правила SemVer для числовых, смешанных и вложенных значений.
Поэтому суффикс имени DEB может отличаться от исходного `rc.1`; точное значение
есть в `debian_version` файла `build-info.json`. Build metadata в Debian-версию
не входит и не повышает приоритет обновления; полная версия остаётся в приложении
и manifest.

```sh
sudo apt install ./xlibrary_0.3.2_amd64.deb
XLibrary
sudo apt remove xlibrary
```

Оба формата сохраняют ABI базовой системы сборки: AppImage не заменяет glibc, графические драйверы и оконный сервер. Автоматическая упаковка и проверка запуска выполняются в контейнере **Debian 13 x86_64** с системными **Qt 6.8.2** и **glibc 2.41**. DEB использует библиотеки Debian 13, а AppImage включает Qt из этой базы; обновлять Qt или glibc в Debian 13 для этих пакетов не требуется. Совместимость DEB с Ubuntu и другими выпусками отдельно не проверяется. При ручной упаковке используйте ту же базу: сборка на более новом дистрибутиве может повысить требования обоих форматов. Для системы старее Debian 13 собирайте пакет на ней с подходящим Qt. Готовые файлы CI доступны в артефакте `XLibrary-linux-x86_64`; автоматической публикации GitHub Release нет.

Если DEB требует `libqt6core6t64 (>= 6.10.2)` или `libqt6gui6 (>= 6.9.1)`,
он собран с Qt новее базы Debian 13. Переустанавливать Qt у получателя или
вручную занижать `Depends` нельзя: бинарник сохраняет требования к ABI.
Пересоберите пакет в Debian 13 (для WSL проверьте `/etc/os-release`
в выбранном дистрибутиве) в новом каталоге, без кэша предыдущего Qt:

```sh
cmake --preset linux-release -B cmake-build-debian13-release \
  -DCMAKE_PREFIX_PATH=/usr -DQt6_DIR=/usr/lib/x86_64-linux-gnu/cmake/Qt6
python3 packaging/build_release.py --build-path cmake-build-debian13-release \
  --format deb --output-path release/debian13
```

Перед публикацией установите полученный DEB в чистом Debian 13 без сборочного
окружения и выполните `QT_QPA_PLATFORM=offscreen XLibrary --check-startup`.

## Windows

Нужны Windows 10/11 x64, Git, CMake 3.21+, компилятор C++23 и **динамический** Qt 6.5+ с Widgets, Concurrent и Network. Для сборки встроенного перевода нужны Qt LinguistTools (`lrelease`); при установке Qt SDK включите инструменты переводов. Для Ninja нужен `ninja.exe` в PATH. При первой конфигурации CMake скачивает SQLite с проверкой хеша.

Версия приложения задаётся только в корневом файле `VERSION` в формате
`major.minor.patch[-prerelease][+build]`. CMake передаёт полную строку приложению,
окну «О программе» и упаковщику; `project()` получает три числа. Ресурсы Windows
и Inno Setup используют числовую четвёрку `major.minor.patch.0`, где каждое число
не больше 65535, и отдельную полную строку продукта. Признак prerelease выставляется
только при наличии prerelease-суффикса. После изменения `VERSION` следующая сборка
автоматически повторяет конфигурацию.

CI использует Qt **6.8.3**, MSVC 2022 x64 и MinGW **13.1.0** из Qt Online Installer. Для MinGW выбирайте комплект Qt `mingw_64` и соответствующий ему MinGW; для MSVC — `msvc2022_64` и Visual Studio 2022 / Build Tools с Desktop development with C++. Не смешивайте ABI или архитектуры. Скрипты упаковки и проверки требуют **PowerShell 7** (`pwsh`), а не Windows PowerShell 5.1. Упаковка извлекает лицензии через `cmake -E tar` настроенного CMake.

## Debug в CLion

1. Установите совместимые Qt и toolchain. В CLion → Settings → Build, Execution, Deployment → Toolchains выберите MSVC x64 или MinGW из того же набора, что Qt.
2. Создайте CMake profile `Debug`: Build type `Debug`, Build directory `cmake-build-debug`, CMake options `-DCMAKE_PREFIX_PATH=<путь к комплекту Qt>`. Например, сам комплект содержит `bin/Qt6Core.dll` и `lib/cmake/Qt6`.
3. В Run/Debug configuration для XLibrary добавьте к PATH каталоги `bin` выбранных Qt и MinGW (либо используйте среду MSVC toolchain). Если Qt не находит платформенный плагин, задайте `QT_PLUGIN_PATH=<путь к комплекту Qt>/plugins` только в конфигурации запуска IDE.
4. Build/Debug компилирует и запускает приложение с библиотеками среды разработки. Копирования DLL после Build больше нет. Запуск EXE из Проводника проверяйте на развёрнутом пакете.

Из PowerShell, подставив собственные пути:

```powershell
$qt = 'C:/Qt/6.8.3/mingw_64'
$mingw = 'C:/Qt/Tools/mingw1310_64/bin'
$env:PATH = "$mingw;$qt/bin;$env:PATH"
cmake -S . -B cmake-build-debug -G Ninja `
  -DCMAKE_BUILD_TYPE=Debug "-DCMAKE_PREFIX_PATH=$qt" `
  "-DCMAKE_C_COMPILER=$mingw/gcc.exe" "-DCMAKE_CXX_COMPILER=$mingw/g++.exe"
cmake --build cmake-build-debug
./cmake-build-debug/XLibrary.exe
```

## Release

Для MinGW используйте ту же среду и отдельную папку:

```powershell
cmake -S . -B cmake-build-release -G Ninja `
  -DCMAKE_BUILD_TYPE=Release "-DCMAKE_PREFIX_PATH=$qt" `
  "-DCMAKE_C_COMPILER=$mingw/gcc.exe" "-DCMAKE_CXX_COMPILER=$mingw/g++.exe" `
  -DXLIBRARY_NATIVE_CPU=OFF
cmake --build cmake-build-release --parallel 4
```

Для MSVC откройте **Developer PowerShell for VS 2022 x64**, затем PowerShell 7 с унаследованной средой:

```powershell
$qt = 'C:/Qt/6.8.3/msvc2022_64'
$env:PATH = "$qt/bin;$env:PATH"
cmake -S . -B build-msvc -G 'Visual Studio 17 2022' -A x64 `
  "-DCMAKE_PREFIX_PATH=$qt" -DXLIBRARY_NATIVE_CPU=OFF
cmake --build build-msvc --config Debug --parallel 4
cmake --build build-msvc --config Release --parallel 4
```

Обычный Build не запускает `windeployqt`, архиватор или Inno Setup. Release сохраняет O2 и IPO/LTO, когда toolchain поддерживает IPO. `XLIBRARY_NATIVE_CPU` должен оставаться OFF для распространяемых файлов. Не переиспользуйте один build-каталог для разных Qt/toolchain.

`cmake --install <build> --config Release --prefix <новая staging-папка>` устанавливает EXE, LICENSE и зависимости Qt через Qt deployment script. Эта низкоуровневая операция поддерживает оба toolchain, но **compiler runtime и материалы для распространения добавляет следующий скрипт**.

## Portable и установщик

Из корня репозитория в PowerShell 7:

```powershell
# MinGW, portable ZIP без установщика:
./packaging/build_release.ps1 -BuildPath cmake-build-release
# MSVC, из developer shell:
./packaging/build_release.ps1 -BuildPath build-msvc
# Установщик дополнительно к portable ZIP (Inno Setup 6.3+):
./packaging/build_release.ps1 -BuildPath build-msvc -Installer `
  -InnoCompiler 'C:/Program Files (x86)/Inno Setup 6/ISCC.exe' `
  -OutputPath release/installer-msvc
```

Скрипт сам собирает Release, выполняет install в новой staging-папке, добавляет runtime и лицензии, проверяет запуск и создаёт ZIP. У MSVC он копирует app-local CRT из `VCToolsRedistDir/x64/Microsoft.VC143.CRT`; вне developer shell передайте `-MsvcRuntimePath <каталог CRT>`. Для MinGW пути DLL запрашиваются у **настроенного** `g++.exe` через `-print-file-name`. Лицензии ищутся в `licenses`, `share/doc`, `share/licenses` выбранного toolchain; для другой раскладки передайте `-CompilerLicensePath <каталог лицензий>`. Нужны как минимум `COPYING3`, `COPYING.RUNTIME` и применимые notices MinGW-w64/winpthreads. Отсутствующие обязательные файлы останавливают упаковку.

Перед упаковкой завершите XLibrary, если запустили его из выбранного каталога
сборки, включая выход через меню трея. Windows блокирует замену работающего
`XLibrary.exe`; упаковщик проверяет доступ к файлу до конфигурации и сборки.
Установленная или portable-копия в другом каталоге не мешает сборке.
Скрипт подготавливает `PATH` выбранного toolchain, Qt, CMake и генератора
до конфигурации, включая проверку IPO/LTO. Вывод configure/build/install
сохраняется в `<BuildPath>/packaging-release.log`; при ошибке сообщение
содержит этап, код возврата и путь к логу. `PATH` восстанавливается при выходе.

По умолчанию результат — `release/v0.4.0-msvc/` или `release/v0.4.0-mingw/`:

- `XLibrary-0.4.0-windows-x64-<compiler>-portable.zip` с корневой папкой приложения;
- `XLibrary-0.4.0-windows-x64-<compiler>-setup.exe`, если задан `-Installer`;
- `SHA256SUMS.txt` для ZIP и установщика.

`-BuildPath` и `-OutputPath` принимают абсолютные пути или пути от корня репозитория. Существующий OutputPath не перезаписывается. После успеха staging удаляется; после ошибки остаётся в `build/release-<id>` для диагностики. Среда PATH восстанавливается и при ошибках. В Git попадают только исходники и скрипты; build/dist/release игнорируются.

`build-info.json` внутри пакета содержит версию, Qt, семейство и версию компилятора, конфигурацию, архитектуру, текущий commit, состояние рабочего дерева и UTC-время упаковки. Для публичного выпуска используйте чистое дерево на нужном коммите и проверьте `source_dirty=false`. Архивы и время сборки не обещают побитовой идентичности; версии и входные архивы фиксируются для повторяемой процедуры выпуска.

## Лицензии и исходники зависимостей

XLibrary имеет MIT-лицензию; это не меняет лицензии зависимостей. Скрипт ориентирован на официальный динамический open-source Qt. Он кладёт соответствующие исходные архивы распространяемых модулей в `sources/`, их тексты лицензий — в `licenses/`, а уведомления и ссылки — в `THIRD_PARTY_NOTICES.txt`. Qt DLL/plugins остаются заменяемыми совместимыми сборками; отладка таких изменений обратным проектированием разрешена.

Для Qt 6.8.3 SHA256 архивов qtbase, qtsvg и qtimageformats записаны в `packaging/qt_sources.json`. Архивы скачиваются с `download.qt.io`, и хеш проверяется **до** распаковки. SBOM копируется из `Qt/sbom`, если поставщик его предоставил; отсутствие SBOM у старых Qt не заменяется вымышленными данными. Полный соответствующий исходный архив сохраняет также third-party attribution и инструкции сборки. Для другой версии Qt сначала добавьте независимо проверенные SHA256 в manifest (или передайте `-QtSourceManifest`). При дополнительных Qt-модулях расширьте сопоставление библиотек/плагинов с исходниками; неизвестная Qt DLL останавливает упаковку.

При собственных изменениях Qt замените manifest/источники на точно соответствующие бинарникам и приложите описание изменений. Перед публикацией проверьте применимые условия всех фактически поставляемых зависимостей, в том числе MinGW-w64/winpthreads и права на распространение Microsoft CRT. Не удаляйте licenses/sources из публичного пакета. Исходники XLibrary доступны в репозитории; SQLite находится в public domain.

## Проверка дистрибутива и пользовательских данных

Распакуйте ZIP в доступный для записи каталог, включая путь с пробелами и Unicode:

```powershell
Expand-Archive ./release/v0.4.0-mingw/*-portable.zip -DestinationPath './build/Проверка пакета'
$package = (Get-ChildItem './build/Проверка пакета' -Directory).FullName
./.github/scripts/check_package.ps1 -PackagePath $package -Compiler mingw
Get-FileHash ./release/v0.4.0-mingw/*-portable.zip -Algorithm SHA256
```

Для MSVC замените каталог и `-Compiler msvc`. Сверьте хеш с `SHA256SUMS.txt`. Проверка проверяет DLL, метаданные и лицензии, запускает копию приложения с очищенным PATH и без Qt-переменных из IDE, из другого рабочего каталога с пробелами/Unicode. `--check-startup` создаёт окно и каталог во временном профиле и завершается с 0; проверяются запуск с флагом portable и без него, а также неизменность существующего portable-профиля. Логи: `build/package-check/`. Скрипт не меняет ваш рабочий пакет.

Перед публичным выпуском дополнительно на чистой Windows без Qt/toolchain:

1. Запустите portable обычным способом. Добавьте приложение, тег, сценарий и измените настройку; завершите XLibrary через меню выхода в трее. Повторно запустите и убедитесь, что данные сохранились в `data/xlibrary.db` и `data/settings.ini` рядом с EXE.
2. Перенесите всю папку в другой путь с Unicode/пробелами и повторите запуск. Текущий рабочий каталог не должен определять расположение данных.
3. Запустите `--check-startup` при существующем каталоге: он не должен менять пользовательские данные. Уберите права записи у тестовой portable-папки: обычный запуск должен сообщить ошибку и не переключаться молча на другой профиль.
4. Установите setup.exe без прав администратора. В `{app}` не должно быть `portable.flag`. Установленная версия сохраняет прежние пути: БД `%LOCALAPPDATA%/XLibrary/xlibrary.db`, настройки `%LOCALAPPDATA%/XLibrary/XLibrary/settings.ini` (Qt AppLocalDataLocation). Portable-профиль от них независим. Проверяйте с резервной копией существующих данных.
5. Повторите проверку сохранения и перезапуска, обновите установку и удалите её. Данные пользовательского профиля должны сохраниться. Схема БД этой задачей не меняется; автоматического переноса между portable и installed нет. Для переноса остановите приложение, сделайте резервную копию и копируйте БД и настройки в соответствующие пути вручную.

CI собирает MSVC и MinGW в Debug/Release, GCC и Clang в Debug/Release.
MSVC Release проходит `cmake --install --config Release`, проверку установленных
Qt DLL и запуск без Qt SDK в `PATH`, из каталога с Unicode и пробелами.
Это проверка CMake install с системным CRT runner, а не автономного portable ZIP
или Inno Setup. Linux AppImage и DEB собираются и проверяются отдельным job.
Release workflow дополнительно проверяет Windows ZIP и тихую установку/удаление
Inno Setup. Интерактивные сценарии установки, сохранения после перезапуска
и отказы ACL остаются ручной проверкой. События, обязательные checks,
кэш и ограничения описаны в [CI/CD](.github/CI.md).

## GitHub pre-release

Подготовка выпуска: [Prepare Release Draft](.github/workflows/release.yml).
Запуск только вручную (`workflow_dispatch`) и только с `main`; версия читается
из `VERSION`, без параметра переопределения и без автоматического изменения файла.
`0.5.0` и `0.5.0+build.1` — stable, `0.5.0-rc.1` и `0.5.0-rc.1+build.1` — prerelease.
Числовые prerelease-идентификаторы с ведущими нулями запрещены SemVer.
Windows ограничивает major/minor/patch диапазоном 0..65535.

Validation проверяет отсутствие тега `v<полная версия>`. Windows и Linux получают
один неизменяемый SHA запуска, даже если за время сборки `main` обновился.
Windows: MinGW 13.1 x64, Qt 6.8.3 (`win64_mingw`), Release, `XLIBRARY_NATIVE_CPU=OFF`, существующий
упаковщик и Inno Setup 6.3.3. Проверяются ZIP, лицензии Qt/MinGW, runtime DLL, startup с очищенным
окружением, установка setup в путь с Unicode/пробелами, совпадение метаданных
установки и ZIP, startup и удаление установки. По уточнённому решению публичные
Windows assets остаются MinGW; обычный CI продолжает проверять MSVC и MinGW.
Проверенные исходные архивы Qt кешируются между успешными Windows release jobs;
ключ зависит от `packaging/qt_sources.json`, а SHA256 проверяется и после
восстановления кеша. В кеш включаются только готовые `*.tar.xz`, без временных
загрузок. При отсутствии кеша действуют ограниченные по времени попытки загрузки.
Linux: Debian 13 x86_64, системный Qt 6.8.2, прежний упаковщик AppImage/DEB,
Xvfb/X11, совпадение встроенных метаданных AppImage с `build-info.json`, установка,
startup и удаление DEB, SHA-256. Проверка DEB здесь выполняется в сборочном
контейнере; дополнительная проверка чистого Debian 13 без SDK/сборочных пакетов
перед публикацией остаётся обязательной по правилам базы совместимости.

Draft job запускается только после успеха обеих платформ. Он скачивает artifacts
именно этого run, проверяет четыре имени, хеши упаковщиков, версию, SHA,
`source_dirty=false`, Release и архитектуру по метаданным, а также версию DEB
через `dpkg-deb`. DEB использует общий Linux `build-info.json` упаковщика;
внутри DEB отдельного commit manifest нет. Версия DEB берётся из существующего
SemVer→Debian преобразования CMake, поэтому prerelease-имя DEB отличается от SemVer.
ZIP дополнительно сверяется со встроенным `build-info.json`.
В загрузку попадает только разрешённый набор:

- `XLibrary-<version>-windows-x64-mingw-portable.zip`;
- `XLibrary-<version>-windows-x64-mingw-setup.exe`;
- `XLibrary-<version>-linux-x86_64.AppImage`;
- `xlibrary_<debian_version>_amd64.deb`;
- `build-info-windows.json`, `build-info-linux.json`;
- единый `SHA256SUMS.txt` для четырёх пакетов и двух файлов метаданных.

После проверки единого SHA256SUMS генерируются GitHub release notes с примечанием
о платформах и профилях. Затем явно создаётся lightweight Git-тег на проверенный SHA,
и `gh release create --verify-tag --draft` создаёт только черновик с нужным
prerelease-флагом. Автоматической публикации нет. После загрузки проверяются Draft,
prerelease, полный список assets, их размеры и digest GitHub. Только Draft job
получает `contents: write`; остальные — `contents: read`. Checkout не сохраняет
credentials, actions закреплены по SHA. Все подготовки сериализованы одной
concurrency group с `cancel-in-progress: false`; GitHub может заменить ожидающий
pending run более новым, но активный run не отменяется.

Первый тестовый запуск:

1. Отдельно согласуйте и внесите изменения в `main` обычным процессом PR.
   Для тестового prerelease задайте в `VERSION` ещё не занятую версию, например
   `0.5.0-rc.1`, и дождитесь обычных CI checks. Workflow сам версию не меняет.
2. Откройте Actions → **Prepare Release Draft** → **Run workflow**, выберите
   **main**. Запишите SHA и ссылку на запуск. Параметров версии нет.
3. Дождитесь успеха Validation, Windows, Linux и Draft. При сбое сборки Draft
   не запускается; тега и черновика этот run ещё не создавал. Artifacts успешных
   платформ сохраняются на 14 дней. Исправьте причину и повторите запуск.
   Если исправление изменяет workflow или упаковщик, после его слияния запустите
   **Run workflow** заново: **Re-run jobs** использует исходный commit старого run.
4. Откройте Releases → созданный **Draft**, проверьте тег, SHA, prerelease,
   notes и семь assets. Скачайте их в одну папку и выполните
   `sha256sum --check SHA256SUMS.txt` (на Windows — `Get-FileHash` и сравнение).
5. Проверьте реальные пакеты на чистой Windows и Debian 13, обновление старой
   MinGW-установки, пользовательский профиль, portable и интерактивные сценарии
   выше. Сохраните результаты. Удалите личные данные/локальные пути из notes,
   если они добавлялись вручную; `build-info.json` описывает среду runner.
6. Тестовый черновик оставьте неопубликованным. Только владелец после проверки
   нажимает **Publish release**, когда действительно решит выпустить эту версию.

### Ошибки после создания тега и повторный запуск

GitHub CLI без `--verify-tag` способен создать тег сам. Здесь тег создаётся явно
на `source_sha`, а `--verify-tag` запрещает CLI выбирать другой commit.
Тег появляется **до** создания Draft. Сбой API, загрузки assets или отмена
на этом этапе могут оставить тег без Draft либо частично заполненный Draft.
Он не публикуется; workflow не удаляет и не перезаписывает теги или Releases.
При повторе сборочных jobs artifacts этого run могут заменяться после успешных
проверок, но тег и Draft автоматически не переиспользуются.
Опубликованный выпуск с тем же тегом никогда не используется для дозагрузки.

Повторный полный запуск останавливается на существующем теге; повтор только
Draft job также останавливается при попытке создать существующий ref. Не считайте
ошибку финальной проверки разрешением публиковать частичный черновик.
Для восстановления владелец должен проверить состояние GitHub, SHA тега и все
assets. Можно вручную завершить и проверить тот же Draft из artifacts исходного
run либо удалить **неопубликованный** Draft и его тег (это отдельные операции),
после чего заново запустить workflow из нужного commit `main`.
Удалять опубликованные или чужие теги нельзя. Если `main` изменился, новый запуск
соберёт уже новый SHA; проверьте `VERSION` и осознанно выберите новую версию либо
завершите первоначальный Draft из его исходных artifacts. Сбой до создания ref
не требует удаления тегов. Автоматического отката/публикации нет.

## Ручная проверка импорта и сканирования

Используйте копию профиля или отдельную portable-папку. JSON формата 1 сохраняет
приложения и назначенные им теги, но не сценарии, настройки, неиспользуемые теги
или историю. Это не полная резервная копия профиля.

1. На Linux добавьте `/usr/bin/sleep`, экспортируйте JSON, импортируйте в пустой
   временный профиль и сравните путь, аргументы, рабочую папку, избранное и теги.
2. Измените тип `favorite` на строку или задайте относительный `path` во второй
   записи. Импорт должен указать запись и поле и не добавить даже первую запись.
   Повторите с неверным тегом, NUL, пустым именем, неверным корневым JSON,
   неподдерживаемой версией и неправильным типом массива `applications`.
3. Выполните сканирование дважды. Сравните отдельные счётчики добавлений, дублей,
   пропусков и ошибок. Откройте подробности из библиотеки и настроек, скопируйте
   отчёт; причины должны включать источники и полные пути.
4. Отмените обнаружение и отдельно запись кандидатов до фиксации. Сравните число
   записей и метаданные с исходными: частичных добавлений быть не должно.
   Сразу повторите поиск: кнопки должны работать. Во время самой фиксации
   отмена уже недоступна; поздний запрос не выдаётся за выполненный откат.

Успешный `--check-startup` не подтверждает эти интерактивные сценарии.

## Ручная проверка обновлений

В «Настройки → Обновление» кнопка «Проверить наличие обновления» запрашивает
публичный GitHub Releases API. Та же проверка автоматически выполняется при
обычном запуске программы. Новая версия предлагается через общий NotificationBanner
со ссылкой на вкладку «Обновление»; загрузка и установка требуют подтверждения.
Во время проверки баннер показывает «Проверка обновлений…» без автоматического
скрытия. Затем тот же баннер показывает результат, включая «Установлена последняя
версия», отсутствие выпусков, ошибку или отмену; для результата включается полоса времени.
При запуске в трей отсчёт скрытого уведомления начнётся после открытия окна.
`--check-startup` не выполняет сетевую проверку обновлений.
Личный токен необязателен. Результат проверки
кэшируется на 60 секунд без токена и на 5 секунд с токеном; ошибки и отмена
тоже сохраняют этот интервал. Кэш хранится в памяти до завершения приложения,
переживает закрытие настроек и разделён для запросов без авторизации и каждого
токена (в ключах кэша используются только SHA-256-отпечатки). Повторное чтение
не продлевает срок кэша. Интервал начинается после завершения или отмены
проверки; параллельные проверки не запускаются. По умолчанию канал Stable исключает предварительные выпуски по флагу GitHub
`prerelease`. Preview включает их; сравниваются версии SemVer из тегов с
необязательным `v`, а не дата публикации. Черновики игнорируются.
Кэш дополнительно разделён по каналу. Смена канала отменяет активный запрос
и убирает доступный установщик предыдущего канала. Помимо запуска, проверку можно повторить вручную.
Закрытие настроек отменяет запущенные из них проверку или загрузку, но не фоновую
проверку при запуске. Уведомление не запускает установку автоматически.

Для установки из приложения нужны Windows x64, совпадающая с текущим каталогом
регистрация Inno Setup в HKCU и установщик текущего toolchain (`mingw`/`msvc`).
Формат имени: `XLibrary-<полная SemVer>-windows-x64-<toolchain>-setup.exe`.
Поддерживаются также прежние имена с числовой версией и необязательным
постоянным `-pre-release`. Build metadata не влияет на выбор более новой версии.
У asset должны быть `state=uploaded`, размер до 512 МиБ и `digest=sha256:<64 hex>`
в API GitHub. Установщик загружается по HTTPS из этого репозитория, переходы
разрешены только к CDN GitHub, размер и SHA-256 проверяются до запуска.
Это проверка целостности относительно метаданных GitHub, не подпись издателя.

**Совместимость опубликованной MinGW-версии.** В исходниках опубликованного
`v0.4.0-pre-release` updater требует asset `*-mingw-setup.exe`. Новые Windows
релизы сохраняют этот toolchain и формат имени, поэтому фильтр установщика
не препятствует обновлению. MSVC-установщик старый MinGW-клиент автоматически
не выберет; по уточнённому решению перехода на MSVC нет и updater не изменён.
Если такой переход понадобится в будущем, старым клиентам потребуется однократная
ручная установка. Существующие MSVC-клиенты также не выберут MinGW asset для
встроенной загрузки: для них остаётся ручной переход на страницу выпуска.
Inno `AppId`, каталог установки, пути БД и настроек сохраняются; схема БД
этой задачей не меняется. Отдельная миграция не требуется. Перед обновлением
сделайте резервную копию и завершите XLibrary. Portable-профиль `data/` остаётся
отдельным и не переносится в installed автоматически. Реальное обновление
с сохранением данных проверяется вручную на Windows: `--check-startup` его
не заменяет.

1. Проверить текущую/более новую локальную версию относительно опубликованных
   релизов: отсутствие предложения понизить версию, возможность повторной проверки.
2. На копии установки с более старой версией проверить подтверждение с номерами
   версий, отмену и повторный запуск загрузки, прогресс и закрытие настроек во
   время запроса. Отказ или отмена не закрывают XLibrary и удаляют временный файл.
3. Согласиться на обновление: после проверки установщика должен открыться обычный
   мастер Inno Setup с прежним каталогом установки, а XLibrary — штатно завершиться.
   Установщик не запускается тихо и не перезагружает ПК. Проверить сохранение профиля
   и запуск новой версии. Успешный запуск мастера не означает завершение установки.
4. Для portable, Linux, отсутствующего установщика или SHA-256 проверить переход
   на конкретный релиз после подтверждения. Portable не превращается в installed.
5. Проверить отключённую сеть, таймаут, лимит API, повреждённый ответ, неверные
   размер/хеш и невозможность запуска EXE: ошибка видима, повторная проверка доступна.
6. Без сохранённого токена несколько раз проверить обновления: в течение 60 секунд
   возвращается прежний результат без новых запросов к GitHub. Закрытие и повторное
   открытие настроек не сбрасывает интервал. После истечения интервала выполняется
   новый запрос. С токеном повторить с интервалом 5 секунд. Проверить также ошибку
   сети и отмену: быстрый повтор не должен обходить ограничение.

Метаданные ограничены 4 МиБ на страницу, 20 страницами по 100 релизов и 60 секундами;
загрузка — 15 минутами и таймаутом бездействия 15 секунд. Частичный файл удаляется;
после успешного запуска установщик остаётся в системной временной папке
`xlibrary-update-*`, чтобы завершение XLibrary не удалило выполняемый EXE.

## Локализация

Английский — базовый язык сообщений; русский каталог translations/xlibrary_ru.ts
компилируется lrelease и встраивается в исполняемый файл. Рядом с программой
не нужны отдельные файлы перевода XLibrary. По умолчанию используется первый
поддерживаемый язык системного списка предпочтений; если подходящего языка
нет или перевод не загружается, используется английский. Настройки → Общие
позволяют выбрать системный язык, English или Русский; нужен перезапуск.

Для добавления сообщений используйте QCoreApplication::translate с контекстом XLibrary и обновляйте
русский TS-каталог. lrelease не запускается в пользовательском приложении.

## Автоматические тесты (v0.7.0)

CTest включён по умолчанию (`BUILD_TESTING=ON`). Дополнительно нужен компонент
Qt Test той же версии Qt, что и приложение. Тесты используют временные профили
и локальные фикстуры; реальный GitHub, Steam, домашний каталог и реестр не нужны.

```sh
cmake --preset linux-debug -DBUILD_TESTING=ON
cmake --build --preset linux-debug --parallel 4
ctest --test-dir cmake-build-linux-debug --output-on-failure
# Аналогично: linux-release, linux-clang-debug, linux-clang-release.
```

Windows, включая multi-config MSVC:

```powershell
cmake -S . -B build -DBUILD_TESTING=ON
cmake --build build --config Release --parallel 4
ctest --test-dir build -C Release --output-on-failure
```

Для сборки только пользовательского приложения/пакета можно передать
`-DBUILD_TESTING=OFF`. Тестовые цели и Qt Test не устанавливаются через
`cmake --install`; штатное развёртывание Qt анализирует только `XLibrary`.
Офлайн-тесты не заменяют ручную проверку установки, Wayland/X11, системных
hotkeys, DPI и нескольких мониторов.


Локальное профилирование без телеметрии:

```sh
cmake --preset linux-debug -DXLIBRARY_BUILD_BENCHMARKS=ON
cmake --build --preset linux-debug --target poll_benchmark
QT_LOGGING_RULES=xlibrary.poll.debug=true ./cmake-build-linux-debug/tests/poll_benchmark
# Для обычного приложения:
QT_LOGGING_RULES=xlibrary.poll.debug=true ./cmake-build-linux-debug/XLibrary
```

Бенчмарк не запускается автоматически через CTest и не устанавливается в пакет.
На Windows исполняемый файл multi-config находится в `tests/Release/`.
Linux portal-тест использует отдельный `dbus-run-session` (пакет `dbus-daemon`
или `dbus-x11`); активная пользовательская D-Bus-сессия не затрагивается.
