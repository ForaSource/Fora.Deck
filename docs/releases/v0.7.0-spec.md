# XLibrary v0.7.0 — Stability & Reliability

> **Техническое задание для Codex**  
> Репозиторий: https://github.com/lappland-open/XLibrary  
> Базовая ветка: `main`  
> Проверенный исходный коммит: `c1fc4383b825fcc8626ebecab78b3c1292365bf9` (v0.6.0).  
> Целевой результат: качественная промежуточная версия **v0.7.0**, повышающая надёжность XLibrary перед публичным v1.0.0.

## 0. Роль и правила работы

Ты — ведущий C++23/Qt 6 разработчик XLibrary. **Реализуй изменения в исходном коде**, проверь их сборкой и тестами, не ограничивайся рекомендациями. Прежде чем редактировать файлы, прочти `AGENTS.md`, `README.md`, `BUILDING.md`, `CMakeLists.txt` и существующие инструкции репозитория. Считай код в рабочей ветке источником истины: если он новее указанного коммита, сначала изучи изменения и адаптируй план.

Ограничения:

- Сохраняй C++23, Qt 6, CMake и текущую архитектуру `src/` (backend), `desktop/` (UI и platform integration), `packaging/` и `.github/workflows/`.
- Поддерживай **Windows (MSVC, MinGW)** и **Linux (X11, Wayland с учётом ограничений окружения)**; не исправляй одну платформу ценой другой.
- Не переписывай крупные модули без необходимости. Предпочитай небольшие, локальные, тестируемые изменения.
- Не вводи тяжёлые зависимости, сетевую телеметрию, облачные сервисы, рекламные интеграции и фоновую отправку данных.
- Не ломай `.xlprofile`, JSON-импорт/экспорт, существующие SQLite-профили и миграции, избранное, теги, сценарии, hotkeys, Steam discovery и browser profiles.
- Сохраняй переводимость пользовательских строк: `QCoreApplication::translate(...)` и обновление русских `.ts` при добавлении текста.
- Не добавляй новые крупные продуктовые функции (Workspaces, файловый индексатор, магазин плагинов и т. п.) — это вне объёма v0.7.0.
- Не выполняй `git push`, не создавай GitHub Release и не делай коммит без отдельного указания пользователя.
- При невозможности выполнить системные/GUI-тесты в среде явно сообщи об этом, а не отмечай их как успешные.

## 1. P0 — Разделение Stable / Preview в проверке обновлений

**Файлы для изучения:**

- `desktop/UpdateChecker.cpp`, `desktop/UpdateChecker.h`
- `desktop/SettingsView.cpp`
- `desktop/DesktopService.cpp` и другие фактические точки вызова `UpdateChecker`
- `src/ProfileSettings.*` при необходимости

**Текущее поведение:** GitHub Releases возвращает `prerelease`, но в `UpdateChecker::finish_reply()` кандидаты выбираются по версии без фильтрации по каналу. Это может предлагать пользователям стабильной версии prerelease.

**Реализовать:**

1. Настройку **Update channel**: `stable` (значение по умолчанию) и `preview` (добровольное включение).
2. В `stable` учитывать только опубликованные GitHub Releases с `draft == false` и `prerelease == false`.
3. В `preview` учитывать как стабильные, так и предварительные версии; выбирать наиболее новую по корректной SemVer-логике.
4. Не полагаться только на суффикс тега: использовать поле GitHub `prerelease` как источник информации о типе релиза. При этом корректно сопоставлять SemVer-теги с `-rc`, `-beta`, `-pre-release` в рамках уже принятой политики версий.
5. Не предлагать downgrade; версию `1.0.0` считать новее `1.0.0-rc.1`.
6. В интерфейсе проверки обновлений явно показывать выбранный канал и статус доступной версии. При переключении канала не возвращать старый кэш другого канала.
7. Учитывать канал при кэшировании результатов вместе с уже используемым контекстом авторизации; не снижать существующую защиту от rate limit.
8. Сохранить текущие проверки URL, SHA-256, размера установщика, поддержки MSVC/MinGW, перенаправлений и требования подтверждения перед установкой.
9. Настройка должна безопасно читаться из старых профилей без миграции SQLite, если достаточно `QSettings`.

**Тесты:** набор релизов `0.7.0` stable, `0.8.0-rc.1`, `0.8.0-beta.2`, `0.6.9` и edge cases: пустой список, неизвестный тег, `draft`, ошибочный JSON, одинаковые версии и смена канала. Логику выбора отделить настолько, чтобы тестировать без настоящего GitHub API и без живой сети.

**Готово, когда:** пользователь Stable никогда не получает предложение установить Preview, а Preview корректно видит новые prerelease; существующая проверка и установка подписанных/неподписанных релизных assets не деградирует.

## 3. P0 — Надёжная активация Quick Search на Linux

**Файлы для изучения:**

- `desktop/LinuxIntegration.cpp`, `desktop/PlatformIntegration.h`
- `desktop/SearchOverlay.cpp`, `desktop/SearchOverlay.h`
- `main.cpp` (`--overlay`, `XDG_ACTIVATION_TOKEN`, single-instance IPC)
- `desktop/SettingsView.cpp` (настройка hotkeys)

**Задача:** решить или максимально корректно обработать ситуацию, когда Quick Search вызывается при активном *другом* приложении: на некоторых Linux/Wayland окружениях окно появляется без фокуса или не получает корректную активацию. Проблема особенно важна на KDE Plasma.

**Реализовать по приоритету:**

1. **Одинаковый сценарий входа:** глобальная команда `XLibrary --overlay` должна адресовать уже запущенный экземпляр и открывать Quick Search, а не требовать фокуса основного окна XLibrary. Сохранить существующее поведение single-instance.
2. **Wayland activation:** проверить фактическую передачу и применение `XDG_ACTIVATION_TOKEN`, использовать поддерживаемые механизмами Qt/compositor запросы активации. Не применять X11 API на Wayland.
3. **GlobalShortcuts portal:** реализовать интеграцию с `org.freedesktop.portal.GlobalShortcuts` там, где сервис и нужная версия интерфейса реально доступны. Предусмотреть жизненный цикл регистрации/отмены, уникальность действий и обработку отказа пользователя/композитора. Не маскировать отсутствие поддержки как успех.
4. **Fallback:** если портал недоступен или не предоставляет необходимую функциональность, показать понятное руководство для KDE/GNOME/Xfce по привязке команды `XLibrary --overlay` средствами окружения. Не пытаться обойти политику фокуса Wayland.
5. **Diagnostics:** если окно показано, но не активировано, оставить ненавязчивое понятное сообщение; не показывать ложную ошибку после успешного получения фокуса.
6. Не ломать X11 реализацию (`XGrabKey`, обработка блокирующих модификаторов, keyboard grabs) и горячие клавиши отдельных приложений/сценариев. Если портал может обеспечить только часть возможностей, документировать точное ограничение.
7. Отдельно протестировать переключение нескольких мониторов и сценарий, когда поверх XLibrary находится другое приложение.

**Ручная матрица приёмки:** KDE Plasma Wayland; GNOME Wayland; Xfce/X11 либо KDE/X11; запуск поверх браузера, редактора, Steam; вызов из системного hotkey; повторный вызов при уже открытом оверлее; Esc; потеря фокуса; несколько мониторов. При недоступности среды документируй `not tested`.

**Готово, когда:** на поддерживаемой конфигурации можно открыть и сразу использовать Quick Search из другого приложения; при объективных ограничениях Wayland пользователь получает рабочий системный fallback вместо иллюзии поддержки.

## 4. P1 — Ограничение использования памяти при просмотре директорий

**Файл:** `desktop/SearchResults.cpp` (`directory_entries()`, `read_path()`, модель результатов).

**Проблема:** `QDir::entryInfoList()` материализует полное содержимое директории до фильтрации по префиксу.

**Реализовать:**

1. Перейти на итеративную обработку (`QDirIterator` или подходящий эквивалент), сохранив текущие правила отображения файлов, директорий, hidden/system и обработки ошибок.
2. Выполнять проверку отмены/поколения запроса **во время** обхода каталога.
3. Ограничить накопление совпадений и общий объём работы на один запрос. Например, максимум **50 результатов** и безопасный предел **20 000 просмотренных элементов**; константы должны быть централизованы и объяснены. Если выбрана иная величина, обоснуй.
4. Если выдача неполная, показать корректный индикатор ограничения и предложить открыть папку. Не говорить «Нет результатов», когда проверена только часть каталога.
5. Сохранить ожидаемый UX: директории выше файлов, предсказуемая сортировка, сохранение полной path identity, переход в каталог, запуск/открытие выбранного файла и поддержка быстрых изменений ввода.
6. Ни файловую систему, ни значки файлов не читать синхронно в UI-потоке при каждом вводе.
7. Покрыть фикстурами директорию с большим количеством файлов, быстрые смены запросов, несуществующий/закрытый каталог и корректное завершение после отмены.

**Готово, когда:** ввод пути в большом каталоге не создаёт память пропорционально всему содержимому и не подвешивает интерфейс.

## 5. P1 — Убрать линейный поиск ID при отрисовке результатов

**Файлы:** `desktop/SearchResults.cpp`, `desktop/LibraryModel.cpp`, `desktop/LibraryModel.h`.

**Текущее поведение:** `SearchDelegate::paint()` перебирает строки `service.model`, чтобы найти совпадающий `application_id` и получить его иконку. Вызов происходит на пути отрисовки каждого результата.

**Реализовать:**

1. Создать быстрый lookup `application_id -> row` или предоставлять готовую иконку по ID из `LibraryModel`.
2. Обновлять индекс при `LibraryModel::replace()` и других операциях, меняющих число/порядок строк.
3. Сохранить асинхронную подгрузку и существующий кэш иконок; не делать `QFileInfo`/диск/сеть из `paint()`.
4. При отсутствующем ID использовать fallback-иконку, не обращаться к невалидному индексу.
5. Добавить регрессионный тест или проверяемый benchmark на каталоге 1 000–10 000 приложений, если тестирование данного класса без GUI затруднено.

**Готово, когда:** стоимость получения иконки для записи поиска не зависит линейно от количества приложений.

## 6. P1 — Безопасная совместимость и ошибки нативных UI-плагинов

**Файлы:** `desktop/MainWindow.cpp` (`load_plugins()`), `desktop/UiRegistry.h`, `desktop/SettingsView.cpp`, `README.md`.

**Текущее поведение:** плагины загружаются из `plugins/`, проверяется IID `org.xlibrary.desktop.UiPlugin/1.0`; исключение из `configure()` может прервать загрузку основного окна. Плагины выполняются внутри процесса, а не в песочнице.

**Реализовать:**

1. Определить явную политику **API/ABI совместимости** нативных плагинов (как минимум версия интерфейса и совместимость с текущей major-версией Qt). Переиспользовать IID и/или metadata `Q_PLUGIN_METADATA` там, где это уместно.
2. Не загружать явно несовместимый плагин; показывать понятное объяснение вместо аварийного завершения.
3. Локализовать **обычные ошибки загрузки и C++ исключения**: один неудачный плагин не должен блокировать старт XLibrary.
4. Исключить частично применённые изменения `UiRegistry`, если `plugin->configure()` выбросил исключение (например, посредством конфигурации во временной копии реестра и публикации только при успехе).
5. Сохранить `--safe-mode`, возможность отключения плагина и отказ от автоматической загрузки неподтверждённых пользовательских модулей.
6. Не обещать защиту от segfault/UB внутри стороннего нативного плагина: это невозможно гарантировать без изоляции в отдельном процессе. Зафиксировать риск и рекомендации по доверенным модулям в README.
7. Если обратная совместимость с существующими плагинами требует legacy-режима, оформить его явно и безопасно, не ломать известные работающие плагины молча.

**Готово, когда:** неработающий или несовместимый плагин можно отключить без потери доступности XLibrary; безопасный режим всегда загружает встроенный UI.

## 7. P2 — Мониторинг процессов: измерение перед оптимизацией

**Файлы:** `src/Manager.cpp` (`initialize()`, `poll()`), `src/Windows/Heartbeat.cpp`, `src/Linux/Heartbeat.cpp`.

В `Manager` опрос каждые 2,5 с объединяет статус запущенных процессов с проверками доступности путей/томов. **Не меняй частоту автоматически без измерений**.

1. Добавь локальные средства профилирования/отладочные метрики времени выполнения `poll()` без отправки телеметрии.
2. Сравни простой и список примерно 255, 1 000 и 10 000 записей, где это практично.
3. Если подтверждён лишний I/O/CPU, раздели дешёвую проверку процессов и более редкую проверку файлов/томов; предусмотри ручное принудительное обновление и обновление по доступным системным событиям.
4. Не меняй пользовательскую семантику `running`, `available`, `volume_unavailable`; не удаляй автоматически приложения из-за недоступного внешнего диска.
5. Если замеры не показывают проблемы, зафиксируй результат и **оставь текущий интервал**.

## 9. Критерии приёмки / Definition of Done

- [ ] Windows MSVC Debug и Release собираются.
- [ ] Windows MinGW Debug и Release собираются либо ограничение точно объяснено с логами.
- [ ] Linux GCC и Clang Debug/Release собираются в поддерживаемой матрице.
- [ ] `clang-format`, `clang-tidy` и существующие workflow-проверки проходят.
- [ ] Добавлены реальные автоматические тесты, они исполняются через CTest локально и в CI.
- [ ] Stable/Preview работают отдельно; prerelease не попадает в Stable.
- [ ] Логика проверки обновлений работает без сети в тестах, не допускает downgrade.
- [ ] Quick Search надёжно активируется с другого окна на заявленных поддерживаемых Linux-конфигурациях либо честно сообщает об ограничении и предоставляет системный fallback.
- [ ] Большие директории не приводят к неограниченному накоплению элементов в памяти.
- [ ] Отрисовка поисковой иконки не выполняет O(N) поиск по всему каталогу.
- [ ] Ошибка конфигурирования одного плагина не оставляет частично применённый UI registry; `--safe-mode` работает.
- [ ] Старые профили, теги, сценарии, Steam-карточки и настройки остаются совместимыми.
- [ ] Нет новых тяжёлых зависимостей и сетевой телеметрии; release packages не включают тестовый runtime.
- [ ] Обновлены документация, переводы и заметки к выпуску.

## 10. Порядок выполнения в Codex

Работай небольшими логическими этапами, **сначала корректность, затем оптимизация**:

1. **Baseline:** изучи архитектуру, собери текущий `main`, перечисли существующие tests/CI и риски; не перезаписывай чужие изменения.
2. **Update channels:** выдели тестируемый выбор релиза, реализуй Stable/Preview и тесты.
3. **Tests & CI:** добавь CTest и начальные независимые тестовые наборы; подключи к матрице.
4. **Linux overlay:** улучши системную активацию и portal/fallback; не нарушай X11.
5. **Search:** исправь обход больших директорий и O(N)-поиск иконок, добавь тесты/измерения.
6. **Plugins:** добавь проверки совместимости, атомарную конфигурацию UI registry и обработку исключений.
7. **Validation:** выполни доступные сборки и тесты, обнови документацию/переводы, сделай итоговую проверку diff.

Не объединяй не связанные исправления в огромные рефакторинги. Старайся не менять публичный API без необходимости. Если конкретная задача требует значительного перепроектирования, выбери минимальную надёжную реализацию и зафиксируй отдельно оставшийся технический долг.

## 11. Формат финального отчёта Codex

В ответе укажи:

1. **Что сделано** — по разделам 1–8, с конкретными файлами и главным изменением поведения.
2. **Что не сделано** — причины, ограничения ОС/композитора, технический долг.
3. **Результаты тестов** — точные команды и `pass/fail/not run` для каждой платформы/конфигурации.
4. **Изменения схемы и совместимость** — были ли миграции, сохранились ли прежние профили.
5. **Известные риски** — кратко и без утверждений, не подтверждённых тестами.
6. **Готовность к v0.7.0** — конкретные блокеры, если они остаются.

**Приоритет:** стабильность запуска, сохранность данных, корректность поиска, предсказуемые обновления и совместимость Windows/Linux. Не заменяй эту работу косметическими изменениями интерфейса.
