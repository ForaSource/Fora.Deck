## Poll measurements and resulting policy

Commands (Debug, Debian 13, GCC 14.2 / Qt 6.8.2):
```sh
cmake -S . -B build -DXLIBRARY_BUILD_BENCHMARKS=ON
cmake --build build --target poll_benchmark --parallel 4
QT_LOGGING_RULES=xlibrary.poll.debug=true build/tests/poll_benchmark
```

Synthetic records use the same existing executable with distinct arguments; this
isolates launch-configuration count and does not model 10,000 distinct network files.
One cold pass and three warm samples per size; figures are wall-clock microseconds,
not a CPU profiler or cross-platform performance guarantee.

| Records | Before warm median (µs) | After warm median (µs) | After first full pass (µs) |
| ---: | ---: | ---: | ---: |
| 0 | 150 | 176 | 725 |
| 255 | 35,203 | 4,845 | 36,324 |
| 1,000 | 138,542 | 18,919 | 138,022 |
| 10,000 | 1,350,070 | 187,026 | 1,362,855 |

The measured cost justified separating availability work: process polling remains
2,500 ms; full filesystem/volume work uses 10,000 ms, force-refresh and directory
events. Watches are bounded to 128 parent directories; periodic checks cover paths
and mount events that cannot be observed. The library's **Refresh availability**
button enqueues `poll(true)` on the worker. `core_test::availability_refresh_and_events`
failed before the split and passes after it, including file removal/recreation and
preservation of the card. No Heartbeat frequency or native process semantics changed.
